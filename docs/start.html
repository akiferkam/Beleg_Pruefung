Beleg-Prüfer: technische Dokumentation

Der Beleg-Prüfer analysiert Rechnungen für die Quellberg GmbH und liefert pro Dokument freigeben oder hinschauen mit nachvollziehbaren Prüfbefunden. Ein Sprachmodell extrahiert strukturierte Daten aus den Dokumentseiten. Die automatische Entscheidung entsteht anschließend ausschließlich durch Python-Regeln.

Diese Dokumentation beschreibt den gelesenen Quellstand vom 5. November 2026. Es wurde keine neue Rechnungsverarbeitung ausgeführt. Aussagen über Prüfungen beschreiben die Implementierung, keine unabhängige Bestätigung steuerlicher Vollständigkeit.

KI, Agenten und Verantwortlichkeiten

Die Anwendung hat eine KI-Extraktionsstufe, aber keine Gruppe autonom zusammenarbeitender Prüfagenten. Claude Vision liest Belege und liefert strukturierte Rohdaten. Die Prüfbereiche A–F sind Python-Funktionen; die automatische Entscheidung berechnet decide.py. Ein optionaler Claude-Skill kann die CLI bedienen, ist aber kein zusätzliches Glied der fachlichen Prüfkette. CodeWiki dient ausschließlich der Erstellung dieser Dokumentation.

Die Cache-Zweige sind Alternativen: Bei einem Treffer entfällt der neue Vision-Aufruf. Im Web kann die automatische Entscheidung auch ohne manuellen Override übernommen werden; die manuelle Stufe ist optional. „Übernehmen“ startet die Pipeline erneut, nutzt dabei gegebenenfalls den Cache und schreibt die Historie. Eine Web-Analyse allein schreibt keine Ledger-Einträge auf die Festplatte.

Drei Bedienwege

  1. Web: Analysieren, Original prüfen, gegebenenfalls manuell entscheiden und anschließend ins Ledger übernehmen.
  2. CLI: Einen Ordner vollständig verarbeiten und das Ergebnis unmittelbar ins Ledger schreiben.
  3. Claude-Skill: Die vorhandene SKILL.md dient als Bedienbeschreibung für einen Agenten, der die CLI aufruft.

Die Web-Vorschau lädt die persistente Historie frisch, verändert aber nur das Ledger im Arbeitsspeicher. Extraktions- und Vorschaubild-Caches können trotzdem auf die Festplatte geschrieben werden. Die Übernahme ist ein neuer Pipeline-Lauf; sie bestätigt kein unveränderliches Vorschauobjekt.

Zentrale Eigenschaften

  • Nicht bestandene BLOCK-Befunde führen zu hinschauen; alle übrigen Befunde bleiben zur Erläuterung sichtbar.
  • Ein Dokument ohne Extraktion führt zu einem Lesbarkeitsbefund, statt eine Modellentscheidung zu übernehmen.
  • Die Historie berücksichtigt auch vorherige Dokumente desselben Laufs.
  • Manuelle Entscheidungen bleiben getrennt vom automatischen Ergebnis gespeichert.
  • Eine Freigabe löst keine Bankzahlung und keinen Export in ein Buchhaltungssystem aus.

Installation und Betrieb

Python-Umgebung unter Windows

Die folgenden Befehle gehören in PowerShell im Projektordner. Sie beschreiben die Einrichtung der Anwendung, nicht des Dokumentationswerkzeugs.

cd "C:\Users\akife\Desktop\beleg_pruefer_akif"
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

requirements.txt enthält Anthropic, PyMuPDF, Pillow, PyYAML, python-dotenv, RapidFuzz, Flask und Flask-CORS. Eine konkrete Mindestversion von Python wird dort nicht festgelegt; der Code verwendet unter anderem moderne Union-Typen.

Für neue Extraktionen wird ANTHROPIC_API_KEY benötigt. Die Anwendung lädt die .env im Projektstamm. Eine neue Datei lässt sich beispielsweise mit notepad .env anlegen; eine vorhandene Datei vorher prüfen und erhalten.

ANTHROPIC_API_KEY=HIER_DEN_EIGENEN_SCHLUESSEL_EINTRAGEN

Der Modellname stammt aus config.yaml unter model.name; im untersuchten Stand ist dort claude-sonnet-5 eingetragen. Ob dieser Bezeichner für das verwendete Konto verfügbar ist, wurde nicht durch einen API-Aufruf geprüft. Modellzugang und API-Schlüssel sind Voraussetzung für eine erfolgreiche neue Extraktion.

Web-Oberfläche im Live-Modus

In einem ersten Terminal im Projektstamm:

.\.venv\Scripts\python.exe api\app.py

Die API bindet an http://127.0.0.1:5050. In einem zweiten Terminal:

cd "C:\Users\akife\Desktop\beleg_pruefer_akif\web"
npm install --legacy-peer-deps
$env:VITE_BELEG_API_URL = "http://127.0.0.1:5050"
npm run dev

Die Projektanleitung nennt http://localhost:8080 für die Oberfläche; maßgeblich ist die tatsächlich von Vite ausgegebene Adresse. Die Umgebungsvariable gilt für den gestarteten Prozess und wird beim Build beziehungsweise Start von Vite eingelesen. Alternativ kann sie in web/.env hinterlegt werden.

Die Oberfläche startet beim Laden eine Analyse. Neue, noch nicht gecachte Dokumente können dabei bereits Vision-Aufrufe auslösen. „Analysieren“ schreibt keine Ledger-Historie, kann aber Extraktionscaches erzeugen.

Demo ohne Backend

Ohne gesetztes VITE_BELEG_API_URL wählt web/src/lib/api/index.ts den Mock-Adapter. Für eine aktuelle PowerShell-Sitzung:

Remove-Item Env:VITE_BELEG_API_URL -ErrorAction SilentlyContinue
npm run dev

Auch in web/.env und anderen Vite-Umgebungsdateien darf dann kein Wert gesetzt sein. Der Demo-Modus verwendet gespeicherte Beispieldaten und bildet keinen echten neuen Extraktionslauf ab.

cd "C:\Users\akife\Desktop\beleg_pruefer_akif"

Dieser Aufruf schreibt direkt ins konfigurierte Ledger. Es existiert in run.py kein Vorschau-Schalter.

Zur Übersicht

Pipeline und Extraktion

scripts/pipeline.py::process_folder ist der gemeinsame Verarbeitungskern. CLI und API unterscheiden sich vor allem bei Eingabeparametern, Speicherung und Präsentation.

Ablauf

  1. Modellkonfiguration, Bestellungen und persistentes Ledger laden.
  2. Mit find_belege direkte Dateien des Ordners alphabetisch sammeln; CSV-Dateien ausnehmen.
  3. Jede Datei über intake.load_document öffnen und ihren SHA-256-Hash berechnen.
  4. Für lesbare Dateien eine gecachte Extraktion laden oder Vision aufrufen.
  5. Die Datensätze nach extrahiertem Rechnungsdatum sortieren; Dokumente ohne Datum folgen danach. doc_id dient als weiteres Sortierkriterium.
  6. Extraktionswerte gegen die vorhandene Textschicht abgleichen, Prüfungen ausführen und Entscheidung bilden.
  7. Für jede vorhandene Extraktion einen Ledger-Eintrag im Arbeitsspeicher ergänzen, auch bei hinschauen.
  8. Das Ledger nur bei commit_to_ledger=True speichern.

Die Reihenfolge beeinflusst Mengen- und Duplikatprüfungen. Ein späteres Dokument sieht bereits die zuvor im selben Lauf erfassten Einträge.

Interne Datenmodelle

Typ Wichtige Felder
PageContent PNG-Seitenbild und vorhandener digitaler Text
IntakeResult doc_id, Dateipfad, Typ, Seiten, Lesbarkeit, Fehler
ProcessedDoc Aufnahme, Hash, Extraktion, Fehler, Befunde, Entscheidung und Zusatzkontext
GroundingReport Übersprungen-Status, geprüfte und nicht wiedergefundene Felder

doc_id ist der Dateiname ohne Endung. Gleiche Dateistämme in verschiedenen Ordnern oder Dateiformaten erhalten dadurch dieselbe ID.

Dateiaufnahme

PDFs werden mit PyMuPDF geöffnet und mit 200 DPI gerendert. Pillow reduziert die längste Bildkante bei Bedarf auf 1.600 Pixel. Eine vorhandene Textschicht wird separat extrahiert. Passwortgeschützte PDFs werden zunächst mit leerem Passwort versucht; andernfalls entsteht ein Lesefehler.

Die Bild-Endungsliste enthält JPG/JPEG, PNG, TIF/TIFF, WEBP und HEIC. Die tatsächliche Dekodierung hängt von Pillow und verfügbaren Formaten ab. Bei Bildern wird nur das geladene Bild in eine Seite überführt; mehrere TIFF-Frames werden nicht durchlaufen. Eine OCR-Textschicht erzeugt diese Stufe nicht.

Nicht unterstützte direkte Dateien werden ebenfalls aufgenommen und führen zu einem A1-Befund. Unterordner werden nicht durchsucht. Ein nicht behandelter Fehler beim Datei-Hash oder beim Laden einer beschädigten Cache-Datei kann dagegen den gesamten Lauf abbrechen.

Vision-Extraktion

extract.py sendet Seitenbilder als Base64-PNGs und ergänzend den digitalen Text an Anthropic.messages.create. Ein erzwungener Tool-Aufruf submit_beleg_extraction liefert die Rohdaten.

Das Schema enthält unter anderem Belegtyp, Lieferant, Empfänger, Rechnungsnummer und -datum, Bestellreferenz, Positionen, Netto/USt/Brutto, Bankverbindung, Reverse-Charge-Signale und manipulation_attempt. Nicht sicher lesbare Werte sollen null sein.

Der Systemprompt behandelt Dokumenttext als Daten und fordert bei anweisungsartigen Texten ein Zitat im Manipulationsfeld. Der Python-Code übernimmt daraus keine direkte Freigabe. extract_document_safe fängt Ausnahmen des Extraktionsaufrufs ab und liefert einen Fehlertext für A2. Eine separate umfassende lokale Schema-Validierung des zurückgegebenen block.input findet in dieser Funktion nicht statt.

Cache

Der Cache liegt normalerweise unter .cache/extracted/<sha256>.json. Eine Regeländerung kann deshalb dieselben Rohdaten ohne erneuten Modellaufruf auswerten. Der Schlüssel berücksichtigt ausschließlich den Dateiinhalt, nicht Modell, Prompt, Schema oder Konfiguration.

CLI --no-cache setzt das Cache-Verzeichnis für diesen Lauf auf None. Der Web-Endpunkt bietet keinen entsprechenden Schalter. results/extracted/<doc_id>.json sind dagegen Ergebnis-Kopien und werden nicht als Hash-Cache gelesen.

Grounding

normalize.check_grounding sucht mehrere deutsche und englische Zahlendarstellungen im normalisierten Text. Geprüft werden Netto-, Steuer- und Bruttobetrag sowie Positionsmengen und Positionssummen. Einstellige ganze Zahlen mit Betrag kleiner 10 werden als zu unspezifisch ausgelassen.

Fehlt digitaler Text, wird die Prüfung als übersprungen behandelt. Sie ist ein textueller Plausibilitätsabgleich; sie weist einem Betrag keine bestimmte semantische Stelle im Dokument zu. Obwohl config.yaml ein Feld grounding_enabled enthält, fragt der untersuchte Pipeline-Aufruf dieses Feld nicht ab.

Quellen

scripts/pipeline.py, scripts/intake.py, scripts/extract.py, scripts/normalize.py.

Zur Übersicht · Prüfkatalog

Prüfkatalog und automatische Entscheidung

checks.run_all_checks erstellt Finding-Objekte mit check_id, level, passed, message und policy_tunable. Ein Befund blockiert genau dann, wenn level == "BLOCK" und passed == False gilt. decide.decide setzt bei mindestens einem blockierenden Befund hinschauen, ansonsten freigeben.

Ausführungsreihenfolge

A1 und A2 werden zuerst geprüft. Schlägt einer fehl, endet die Prüfung dieses Dokuments. Danach folgen A3, A4 und A5. Ist das Dokument keine Rechnung, endet der weitere Katalog nach diesen Prüfungen. Fehler in A4 oder A5 verhindern dagegen nicht die anschließenden B–F-Prüfungen einer Rechnung.

A: Lesbarkeit und Format

ID Implementiertes Verhalten
A1 Datei konnte geöffnet und aufgenommen werden
A2 Extraktion vorhanden, kein Extraktionsfehler und kein Unlesbarkeitsflag
A3 document_type ist exakt Rechnung
A4 Behauptete Gesamtseitenzahl entspricht der gelieferten Seitenzahl; ohne Angabe entfällt der Vergleich
A5 Geprüfte Zahlen sind in der digitalen Textschicht wiederzufinden; ohne Textschicht übersprungen

B: Formale Angaben

ID Implementiertes Verhalten
B1 Erstes Wort des konfigurierten Firmennamens im Empfängernamen und konfigurierte Adressfragmente vorhanden
B2 Name und Adresse des Lieferanten vorhanden
B3 Lieferanten-Steuerkennung und ein bekannter Kennungstyp vorhanden
B4 Rechnungsnummer sowie ISO-Datum vorhanden; Datum nicht in der Zukunft
B5 Netto, USt-Satz, USt-Betrag und Brutto nicht None
B6 Bei 0 %: Reverse-Charge-Hinweis und Steuerkennungen von Empfänger und Lieferant vorhanden
B7 Leistungsdatum wird als Information ausdrücklich nicht geprüft

B6 vergleicht die Empfängerkennung trotz übergebenem Konfigurationswert nicht mit der Firmen-USt-ID. Jeder 0%-Fall wird auf die genannten Reverse-Charge-Angaben geprüft; andere steuerliche Gründe für 0 % werden nicht gesondert modelliert. Die Dokumentation beschreibt diese Regeln, ohne daraus eine vollständige steuerrechtliche Prüfung abzuleiten.

C: Arithmetik

ID Implementiertes Verhalten
C1 Je vollständiger Position: abs(Menge * Einzelpreis - Positionssumme) <= abs(Menge) * Toleranz
C2 Summe vorhandener Positionssummen gegen Netto; bei unzureichenden Daten INFO
C3 USt-Satz in der konfigurierten Liste; fehlender Satz wird bereits in B5 behandelt
C4 Netto * USt-Satz / 100 gegen USt-Betrag
C5 Netto + USt gegen Brutto
C6 Eine angegebene Währung muss EUR sein; ein vorhandenes Brutto muss positiv sein

C1 lässt Positionen mit fehlenden Operanden aus. C6 blockiert eine leere Währung nicht. Die Berechnungen verwenden Python-Fließkommazahlen und absolute Toleranzen.

D: Bestellabgleich

ID Implementiertes Verhalten
D1 Fehlende Bestellreferenz je nach Policy BLOCK oder INFO
D2 Angegebene Referenz muss in der CSV existieren; unbekannte Referenz bleibt unabhängig von D1 blockierend
D3 Lieferantenvergleich mit RapidFuzz token_set_ratio, Standardschwelle 70
D4 Einzelpreise zugeordneter Positionen gegen Bestellpreis
D5 Bereits erfasste Menge plus aktuelle passende Menge darf Bestellmenge nicht überschreiten
D6 Wert zusätzlicher Positionen im Verhältnis zum Bestellwert
D7 Information über Rahmenbestellung

D3–D7 werden nur bei gefundener Bestellung ausgeführt. Positionen zählen ab einem fest im Code definierten Fuzzy-Score von 40 als passend. Ein Bestell-Einzelpreis von 0 kennzeichnet einen Rahmenvertrag; D4 und D5 entfallen dann. Zusatzpositionen bei einem Referenzwert kleiner oder gleich 0 bleiben manuell zu prüfen. Gleiche Rechnungsnummern werden bei der historischen Mengenberechnung ausgeschlossen.

E: Duplikate und Auffälligkeiten

ID Implementiertes Verhalten
E1 Identischer Datei-Hash bereits im Ledger
E2 Gleicher normalisierter Lieferantenname und gleiche Rechnungsnummer
E3 Gleicher Positionsfingerabdruck und kompatibler Bruttobetrag unter anderer Rechnungsnummer
E4 Vorhandene IBAN hat eine gültige Modulo-97-Prüfsumme
E5 Vorhandene IBAN stimmt mit einer bekannten IBAN des Lieferanten überein
E6 Extrahiertes Manipulationszitat führt zu einem blockierenden Befund

Fehlende IBAN oder fehlende Bankhistorie werden als INFO behandelt. E3 filtert nicht zusätzlich auf Lieferant oder Bestellnummer. E6 hängt davon ab, ob die Extraktion einen Versuch erfasst.

F: Geschäftsregeln

F1 blockiert, wenn das Brutto größer als die Freigabegrenze ist; Gleichheit blockiert hier nicht. F2 zeigt vorhandene Skontobedingungen nur als Information an.

Standardwerte aus config.yaml

Policy Wert
Zusatzpositionen 10 % des Bestellwerts
Bestellbezug erforderlich true
Obligatorische Prüfung oberhalb 50.000 € brutto
Positionsarithmetik je Einheit 0,005 €
Nettosumme 0,05 €
USt-Betrag / Bruttobetrag jeweils 0,02 €
USt-Sätze 0, 7, 19

Zur Übersicht · Ledger und Berichte

Ledger, manuelle Entscheidungen und Berichte

Historie

scripts/ledger.py::Ledger lädt eine JSON-Liste von LedgerEntry-Datensätzen. Jeder Eintrag enthält Dokument-ID, Datei-Hash, Lieferant, Rechnungsnummer und -datum, Bestellreferenz, Beträge, Gesamtmenge, Positionsfingerabdruck, normalisierte IBAN, automatische Entscheidung und UTC-Verarbeitungszeit.

Eine fehlende Datei bedeutet eine leere Historie. Eine ungültige vorhandene JSON-Datei wird nicht automatisch repariert. save schreibt die gesamte Liste neu; Datenbanktransaktionen, Dateisperren und atomare Austauschdateien sind nicht implementiert.

Welche Dokumente werden erfasst?

Die Pipeline ergänzt für jede vorhandene Extraktion einen Eintrag, unabhängig von der Entscheidung. Damit können auch hinschauen-Belege und extrahierte Nicht-Rechnungen die spätere Historie beeinflussen. Es gibt an dieser Stelle keinen Filter „nur freigegebene Rechnungen“.

record hängt Einträge an, ohne vorherige Einträge zu ersetzen oder Duplikate abzuweisen. Ein wiederholter Commit kann dieselben Dokumente erneut hinzufügen. Die Prüfungen melden zwar Duplikate, verhindern das anschließende Anhängen aber nicht.

Bei gefundener Bestellung verwendet ledger_entry_for nur die Mengen der zur Bestellung passenden Positionen. Ohne gefundene Bestellung werden alle extrahierten Positionsmengen summiert. Historische Mengen berücksichtigen alle Entscheidungen und schließen Einträge mit der aktuellen Rechnungsnummer aus.

Inhaltsfingerabdruck

line_items_fingerprint normalisiert Positionsbeschreibungen durch Kleinschreibung und äußeres Trimmen, rundet Mengen und Einzelpreise auf vier sowie Positionssummen auf zwei Nachkommastellen, sortiert die Tupel und bildet einen SHA-256-Hash des JSON-Texts. Rechnungsnummer, Datum, Lieferant und Layout gehören nicht zum Fingerabdruck.

find_content_duplicate sucht denselben Fingerabdruck unter anderer Rechnungsnummer. Sind beide Bruttobeträge vorhanden, darf ihre Differenz höchstens 0,02 € betragen.

Vorschau und Übernahme

Jeder Aufruf lädt die Historie erneut. In einer Vorschau sehen spätere Dokumente die vorherigen desselben Laufs, ohne dass diese Ergänzungen dauerhaft gespeichert werden. Ein Commit führt den Lauf erneut aus und kann bei inzwischen geänderter Historie andere Ergebnisse liefern.

Manuelle Entscheidungen

overrides.py speichert unter results/overrides.json pro doc_id die Entscheidung, Notiz, ursprüngliche automatische Entscheidung und einen UTC-Zeitpunkt. Eine erneute Übersteuerung derselben ID ersetzt den bisherigen Override; eine unveränderliche Versionshistorie gibt es nicht.

Die API zeigt entscheidung für das automatische Ergebnis und endstatus für das Ergebnis nach Override. Im Frontend gilt entsprechend manual?.entscheidung ?? autoDecision.

Wichtig für die Interpretation: Beim Web-Commit wird das Ledger durch die Pipeline bereits mit der automatischen Entscheidung gespeichert. Anschließend überlagert die API die Berichtszeilen mit manuellen Entscheidungen. Der Ledger-Status und der CSV-Endstatus können deshalb voneinander abweichen. Die CLI liest Overrides nicht ein.

Ergebnisdateien

Datei Inhalt
results/ergebnis.csv Semikolon-getrennte Tabelle mit UTF-8-BOM
results/ergebnis.md Zusammenfassung und Detailbefunde
results/extracted/<doc_id>.json Kopie der Rohdaten einer erfolgreichen Extraktion
results/overrides.json Persistente manuelle Übersteuerungen
.cache/extracted/<hash>.json Wiederverwendbare Rohdaten nach Dateiinhalt
.cache/thumbs/ Vorschaubilder der Web-API

Die CSV-Spalten sind doc_id, datei, entscheidung, lieferant, rechnungsnr, betrag_brutto_eur, bestellnummer, gruende, info_notes, quelle, automatisch_war und manuelle_notiz. Bei normalen CLI-Zeilen bleiben die Zusatzspalten für manuelle Herkunft leer.

Bei gleicher Dokument-ID können Extraktionskopien und Overrides kollidieren. Berichte werden pro Lauf neu geschrieben; sie sind kein vollständiges Ereignisprotokoll aller bisherigen Läufe.

POST /api/analyze JSON: folder, policy, beide optional Pipeline ohne persistente Ledger-Schreibung; Cache-Schreibung möglich
POST /api/commit wie Analyze Pipeline mit Ledger-Schreibung, Berichten und Extraktionskopien
POST /api/upload Multipart-Feld files, mehrfach Dateien in einen neuen Batch-Ordner schreiben
POST /api/override JSON mit Dokument-ID und Entscheidung Manuellen Override sofort speichern
GET /doc?path=... Dateipfad Originaldatei ausliefern
GET /thumb?path=... Dateipfad PNG-Vorschaubild liefern beziehungsweise erzeugen

Analyse-Beispiel

{
  "folder": "C:/Users/akife/Desktop/beleg_pruefer_akif/belege",
  "policy": {
    "extra_items_tolerance_pct": 10,
    "mandatory_review_amount_eur": 50000,
    "no_po_match_means_hinschauen": true,
    "line_arithmetic_tolerance_per_unit_eur": 0.005
  }
}

Ohne Ordner wird belege/ im Projektstamm verwendet. Die Bestell-CSV wird zuerst im gewählten Eingabeordner gesucht, danach über den konfigurierten Projektpfad. Ein nicht vorhandener Ordner liefert HTTP 400.

apply_overrides erlaubt nur die vier oben genannten Policy-Felder. Die drei Zahlenwerte werden mit float konvertiert; der Bestellbezug mit bool. Clients müssen dafür echte JSON-Booleans senden: Ein String wie "false" wäre in Python wahr. Eine umfassende Wertebereichsvalidierung ist nicht vorhanden.

Die Overrides gelten nur für diesen Lauf. Ein Endpunkt zum Speichern dieser Policy in config.yaml existiert im untersuchten Stand nicht.

Antwortformat

{
  "docs": [],
  "summary": {"freigeben": 0, "hinschauen": 0, "gesamt": 0},
  "committed": false,
  "policy_used": {}
}

Dies ist ein Formbeispiel mit leerer Dokumentliste. Tatsächliche Dokumentobjekte enthalten doc_id, datei, pfad, entscheidung, endstatus, manuell, Lieferanten- und Rechnungsfelder, Beträge, Positionen, gruende, info_notes und fehler. Befunde werden als { "id": "A1", "nachricht": "..." } übertragen. Die Liste wird nach Dokument-ID sortiert, unabhängig von der internen Prüfungsreihenfolge.

summary zählt die nach manuellen Overrides wirksamen Endstatus. policy_used enthält die tatsächlich verwendete Policy inklusive weiterer konfigurierter Werte.

Upload

Uploads werden unter api/uploads/<Zeitstempel>-<Zufall>/ gespeichert. Der Server übernimmt den Basisdateinamen und gibt folder sowie dateien zurück. Der Client muss den zurückgegebenen Ordner für die folgende Analyse und den Commit verwenden.

Ein Request ohne Dateien liefert HTTP 400. Die Upload-Funktion besitzt keine eigene Liste zulässiger Dateiendungen und keine konfigurierte Größenobergrenze. Die spätere Aufnahme bewertet nicht unterstützte Formate.

Manuelle Entscheidung

{
  "doc_id": "beispielrechnung",
  "decision": "freigeben",
  "note": "Original geprüft",
  "original_decision": "hinschauen"
}

Ohne Dokument-ID oder mit einer anderen Entscheidung als freigeben/hinschauen folgt HTTP 400. Der Server prüft hier nicht, ob die Dokument-ID tatsächlich Teil eines zuvor analysierten Laufs war.

Dateiabruf und Betriebsgrenzen

/doc und /thumb erlauben PDF, JPG/JPEG, PNG, TIF/TIFF und WEBP. Eine fehlende Datei führt zu 404, eine andere Endung zu 403. Der Dateipfad wird auf Existenz und Endung geprüft, jedoch nicht auf Zugehörigkeit zu einem bestimmten Projektordner beschränkt.

CORS ist für /api/* auf lokale HTTP-Ursprünge mit Port beschränkt. Authentifizierung und Nutzerrollen sind nicht implementiert. Die lokale Bindung gehört zum vorgesehenen Betriebsmodell. Da Ledger und Overrides ohne Sperren als JSON geschrieben werden, sind konkurrierende schreibende Requests nicht transaktional abgesichert.

Web-Oberfläche und Zustand

Die Oberfläche verwendet React 19, TanStack Router/Start, Vite, Tailwind und Radix-Komponenten. Anwendungsbezogene Komponenten liegen unter web/src/components/beleg/, allgemeine UI-Bausteine unter web/src/components/ui/.

Seiten

Route Aufgabe
/ Dashboard mit Kennzahlen und Aktivitäten
/pruefen Warteschlange offener Dokumente
/belege/$docId Einzelbeleg mit Befunden, Positionen und Originalvorschau
/freigegeben Ansicht entschiedener beziehungsweise freigegebener Dokumente
/hochladen Datei-Upload und anschließende Analyse

Die Routendateien befinden sich unter web/src/routes/. routeTree.gen.ts ist der generierte Routenbaum. Der Router und die Root-Route stellen das gemeinsame Layout und den Anwendungsprovider bereit.

API-Abstraktion

web/src/lib/api/types.ts definiert BelegApi, BelegResult, PolicyOverrides und weitere gemeinsame Typen. api/index.ts wählt abhängig von VITE_BELEG_API_URL den REST- oder Mock-Adapter.

Der REST-Adapter übersetzt deutsche/snake_case-Serverfelder in die Frontend-Struktur, etwa doc_id nach docId, entscheidung nach autoDecision und gruende[].nachricht nach blockingReasons[].message. Original- und Vorschau-URLs entstehen aus dem von der API gelieferten Dateipfad.

Der Adapter setzt currency fest auf EUR, statt einen Serverwert zu übernehmen. Die UI-Währungsanzeige ist damit kein zusätzlicher Nachweis der tatsächlichen Belegwährung.

Zentraler Store

BelegProvider in web/src/lib/beleg-store.tsx verwaltet den letzten Lauf, Dokumente, Ladezustand, Policy, aktuellen Eingabeordner, Änderungsstatus, letzten Commitzeitpunkt und Aktivitäten.

Aktion Ablauf
analyze API aufrufen, Ergebnis ersetzen, als unübernommene Vorschau markieren
commit Pipeline-Commit anfordern, Ergebnis ersetzen, Zeit merken und Aktivität erzeugen
decide Override serverseitig speichern und manuelle Entscheidung im lokalen Ergebnis ergänzen
setPolicy Werte im Browser speichern und sofort erneut analysieren
upload Dateien hochladen, Batch-Ordner merken und genau diesen Ordner analysieren

API-Fehler werden als Toast-Nachricht angezeigt; finally setzt den Ladezustand zurück. RunBar zeigt Vorschau/Übernahmezustand und öffnet vor dem Commit einen Bestätigungsdialog.

Persistenz im Browser

Local-Storage-Schlüssel Bedeutung
beleg.policy.v1 Vier UI-Policy-Werte
beleg.folder.v1 Letzter Eingabeordner
beleg.activity.v1 Bis zu 60 lokale Aktivitäten
beleg.lastCommit.v1 Letzter im Browser gemerkter Commitzeitpunkt

Diese Werte sind browserbezogen. Sie ersetzen weder Backend-Konfiguration noch ein zentrales Auditprotokoll. Die vollständige Dokumentliste wird nach dem Laden neu angefragt.

Beobachtete Besonderheiten

  • defaultPolicy() des REST-Adapters liefert die Mock-Standardwerte; es liest nicht die aktuelle config.yaml vom Server. Der Store initialisiert ebenfalls mit DEFAULT_POLICY beziehungsweise Local Storage und überträgt diese vier Werte an die API.
  • Beim ersten Effekt wird zwar ein gespeicherter Ordner in den State geladen, analyze(p) verwendet aber noch den im ursprünglichen Callback erfassten Ordner. Der erste Lauf nach Neuladen kann deshalb den Backend-Standardordner analysieren. Spätere Aufrufe nutzen den aktualisierten State.
  • Die manuelle Entscheidung wird bereits beim Klick serverseitig gespeichert. „Noch nicht im Ledger“ bedeutet daher nicht, dass keinerlei Datei verändert wurde.
  • Der finale UI-Status wird mit finalDecision aus manueller oder automatischer Entscheidung berechnet. Die automatische Begründung bleibt dabei verfügbar.

Evaluation, Wartung und Grenzen

Vorhandene Auswertung

eval/eval.py vergleicht eine Ergebnis-CSV mit einer Ground-Truth-CSV über doc_id. Beide Dateien werden mit Semikolon als Trennzeichen und UTF-8-BOM-Unterstützung gelesen.

python eval\eval.py --ergebnis results\ergebnis.csv --ground-truth eval\ground_truth.csv

Die Ergebnisdatei benötigt entscheidung, die Ground Truth erwartete_entscheidung. Als positives Ereignis gilt hinschauen:

Kennzahl Bedeutung
TP Erwartet hinschauen, erhalten hinschauen
TN Erwartet freigeben, erhalten freigeben
FP Unnötige manuelle Prüfung
FN Erwartet hinschauen, trotzdem freigegeben

Der Bericht betont FN als gefährliche Fehlfreigabe. Fehlende IDs erzeugen eine Warnung und werden nicht in den Nenner der Accuracy aufgenommen. Doppelte IDs in einer CSV überschreiben sich im eingelesenen Dictionary. Der Evaluator setzt bei Fehlfreigaben keinen eigenen fehlschlagenden Prozess-Exitcode; seine Ausgabe muss daher für CI gezielt ausgewertet oder der Evaluator erweitert werden.

Die Projekt-README nennt für die 16 mitgelieferten Testbelege 3 Freigaben und 13 Fälle zum Hinschauen. Dies ist ein dokumentiertes Beispielergebnis und keine bei der Erstellung dieser Wiki neu durchgeführte Vision-Auswertung.

Weitere Testwerkzeuge

eval/generate_synthetic_set.py erzeugt synthetisches Testmaterial; eval/generate_injection_demo.py dient einem Manipulationsbeispiel. Die Generatoren gehören zum Test- und Demonstrationsbereich und sind kein Bestandteil des normalen Web-Requestpfads.

Eine neue Regel ergänzen

  1. Regel im passenden Modul von scripts/checks/ als Funktion mit Finding-Rückgabe implementieren.
  2. Eindeutige Prüf-ID, aussagekräftige Nachricht und bewusste Stufe BLOCK oder INFO wählen.
  3. Aufruf in checks.run_all_checks an einer zur Datenverfügbarkeit passenden Stelle einfügen.
  4. Falls nötig den Schwellenwert in config.yaml ergänzen und explizit übergeben.
  5. Grenzfälle und fehlende Eingabewerte anhand isolierter Datensätze überprüfen.
  6. Für eine neue UI-Policy zusätzlich API-Freigabeliste, TypeScript-Typen und Oberfläche anpassen.

Extraktion erweitern

Neue Felder gehören zunächst in EXTRACTION_SCHEMA und gegebenenfalls in den Prompt. Danach müssen nachgelagerte Prüfungen und API-/UI-Abbildungen angepasst werden. Bei einer Änderung am Schema muss der dateiinhaltsbasierte Cache berücksichtigt werden: Alter Dateiinhalt kann weiterhin alte Extraktionsdaten liefern.

Wichtige Grenzen des aktuellen Codes

Bereich Grenze
Steuerliche Felder Leistungsdatum nicht extrahiert/geprüft; Reverse-Charge-Prüfung vereinfacht
Datenqualität Nicht jedes fehlende Feld blockiert; einige Rechenprüfungen werden ausgelassen
Grounding Textsuche ohne semantische Feldzuordnung; ohne Textschicht übersprungen
Cache Modell-, Prompt- und Schemaversion nicht im Cache-Schlüssel
Persistenz JSON-Dateien ohne Transaktionen und Sperren; wiederholtes Anhängen möglich
Manuelle Entscheidung Override nach Dokument-ID, keine unveränderliche Änderungshistorie
Mehrbenutzerbetrieb Keine Benutzerverwaltung; parallele Schreibzugriffe nicht abgesichert
Datenvertrag Begrenzte Requestvalidierung; einige Frontend-Defaults stammen aus dem Mock-Adapter

Die konkreten Auswirkungen sind in Prüfkatalog, Ledger, API und Frontend erläutert. Diese Punkte beschreiben den untersuchten Stand; im Zuge dieser Dokumentation wurden keine Anwendungsfunktionen geändert.
